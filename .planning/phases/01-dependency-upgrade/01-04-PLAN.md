    How the soak is judged. The fourth Task 3 check implements these rules. It reads only the evidence files, so re-running it is safe:

The new pod polls every feed once as soon as `ApplicationReadyEvent` fires, because the first run of `scheduleAtFixedRate(task, interval)` is immediate. That happens before `rollout status` returns, and after deploy-time whatever the feed's `pollIntervalMinutes`. So feeds whose interval exceeds the soak need no exemption and no longer wait.
    - The field is `lastPolledAt`, not `lastSuccessfulPollAt`. Every outcome sets `lastPolledAt`, while a 304 leaves `lastSuccessfulPollAt` behind. A failed poll raises `errorCount`, so `errorCount` 0 together with `lastPolledAt` after deploy-time means no post-deploy poll failed.
    - Only a 200 resets `errorCount`. A healthy feed that hits one transient error and then answers 304 stays at `errorCount` 1 without failing again. Recovery is therefore judged by comparing two captures, not by `errorCount` alone.

    For each feed with `errorCount` 0 in `feeds-before.json`, the check assigns exactly one class:
    - `clean`: `errorCount` 0 and `lastPolledAt` after deploy-time. Passes. Those whose `lastSuccessfulPollAt` is not after deploy-time are also counted as `only304`.
    - `notPolled`: absent, or `lastPolledAt` not after deploy-time. Fails, because the new release never polled it.
    - `pending`: `errorCount` above 0 and not yet rechecked. Fails until the recheck below is done.
    - `recovered`: in `feeds-recheck.json`, `errorCount` is 0, or `lastPolledAt` advanced without `errorCount` rising. Passes.
    - `remoteSide`: not recovered, and the workstation probe got no 2xx. Passes, and is reported with the probe code and `lastError`, because the remote is failing for every client, not just the app.
    - `regression`: re-polled during the recheck, failed again, and the remote answers the workstation with a 2xx. Fails as a probable upgrade regression.
    - `unresolved`: not re-polled within the recheck window, because its interval is longer than the cap, while the remote answers with a 2xx. Passes the check, but report it to the user with its `lastError` as needing a look.

## Flagged Assumptions (edge probe: UPG-03, unclassified, left unresolved)

The edge probe could not classify UPG-03. Per the no-silent-drop rule it stays **unresolved**. The planner sees these candidate edges but does not auto-resolve them:
1. **Redis cache compatibility across Jackson 3.0.4 → 3.1.5 (research A3).** This is unverified until production reads old cache entries. The mitigation is a cache-only FLUSHALL, and only on observed errors.
2. **New articles arriving during the soak window** depends on publishers. The automated checks prove polling succeeds; only the human check can confirm that "new articles appear in the reader".
3. **A healthy feed failing during the window for reasons unrelated to the upgrade** (a remote outage or rate limit). The soak check separates these cases mechanically. A feed that recovers on its next scheduled poll passes. A feed whose remote also fails a workstation probe is reported as `remoteSide`. Only a feed that fails again while its remote answers the workstation counts as a regression. A feed not re-polled within the 60-minute recheck cap is reported to the user as `unresolved` rather than judged automatically. The probe's 2xx test is a heuristic: a remote that rate-limits only the cluster's egress would read as a regression. That is why a regression is reported with a rollback recommendation and never rolled back automatically.
4. **Real-network behavior changes that only production can show**: Reactor Netty 1.3.3 → 1.3.7, and the now-bound 30s read timeout (research A5, the D-02 intended change). The before/after errorCount comparison is the detector.
