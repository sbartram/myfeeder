<objective>
Close UAT gap G-05-7 (review finding WR-02). Today the Priority cursor is an article id, and each "Load more" re-reads that article's live score. If the score drops between pages (a topic weight lowered, a re-score, or from Phase 6 every thumbs vote), the next page starts below the article's new position, and every row between its old and new rank is silently skipped.

The fix makes the cursor carry the sort tuple `(sort_score, sort_date, id)` exactly as it was served, encoded as an opaque URL-safe string. The next page compares against those literal values. This keeps the walk monotone in the ranking the user is looking at. It is the fix recommended in 05-REVIEW.md WR-02 and listed as the gap's `missing` items in 05-UAT.md.

Purpose: PRIO-06 (paging across the boundary with no gaps) and PRIO-05 (triage inside Priority, where votes and re-scores change scores mid-walk) must hold under concurrent score changes, before Phase 6 makes those changes routine.

Decision note: this amends one element of the 05-CONTEXT R4 decision. The user chose "fix WR-02 now" in UAT test 7, and the gap requires the cursor to carry the tuple, so R4's "Long article-id cursor" changes for the Priority endpoint only. Everything else in R4 is kept:
- `PaginatedResponse` itself stays unchanged. Priority gets a sibling record with the same `{items, nextCursor}` JSON shape.
- The keyset tuple and its DESC order are the same.
- A cursor article that was read still continues.
- A cursor article that is gone still restarts from page 1 (404).
- The client still dedupes by id.

The user deferred WR-01 and WR-03. This plan does not touch them.

Output: the served-tuple cursor end to end (SQL → service → controller → JSON → SPA), with the gap's required test at the HTTP level and at the SQL level, plus codec tests.
