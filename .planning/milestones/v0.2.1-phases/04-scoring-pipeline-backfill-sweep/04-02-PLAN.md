<objective>
Build the database side of the scoring queue: the one eligibility predicate, the write-once upserts, the selection queries, and the count and Re-score SQL that the status and Re-score endpoints will reuse. All of it is proven against real Postgres.

Purpose: the design makes the database the queue's source of truth (research R3, "the pipeline's correctness lives in SQL"). Keeping every query in one store around one predicate constant is what makes D-02 ("what's shown is exactly what gets reset") and D-12 ("both counts use the eligibility predicate") true by construction. Building it complete in wave 1 means the scorer (04-03), the status counts (04-06) and the Re-score backend (04-08) can run in parallel in wave 2 without touching this file.

Output: `MyfeederProperties.Interest`, `ArticleScoreStore` (JdbcClient), `ArticleScoreStoreTest`.
</objective>
